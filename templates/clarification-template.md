# 澄清问题模板

澄清闸门生成交互问题和澄清会话产物时使用以下结构。

## 候选问题队列

各阶段先产出候选问题，不直接触发交互。

```markdown
| 问题ID | 检查点 | 来源阶段 | 问题 | 影响 | 阻塞级别 | mustAsk | 建议选项 | 关联需求依据 |
|---|---|---|---|---|---|---|---|---|
```

`mustAsk` 只有在问题为 `Blocking`，且不确认会导致编造规则、漏掉高风险覆盖或无法判断范围时才写 `是`。

## AskUserQuestion 问题结构

只有 `mustAsk=是` 的问题才映射到 Claude Code 的 `AskUserQuestion`：

```json
{
  "questions": [
    {
      "header": "优惠叠加",
      "question": "会员折扣和优惠券是否允许同时叠加？",
      "options": [
        {
          "label": "按活动配置",
          "description": "测试点需要覆盖配置开启、关闭及规则变更"
        },
        {
          "label": "允许叠加",
          "description": "两类优惠可以同时生效"
        },
        {
          "label": "不允许叠加",
          "description": "两类优惠互斥，只能生效一种"
        },
        {
          "label": "暂不确认",
          "description": "作为待确认风险点继续，不沉淀为业务规则"
        }
      ],
      "multiSelect": false
    }
  ]
}
```

宿主 UI 应保留自定义回答入口；自定义回答按用户原文写入澄清会话产物。

## 澄清会话产物

```markdown
# <需求名称> 澄清会话

## 基本信息

- 需求文档：
- 生成时间：
- 当前检查点：
- 当前状态：Pending / Answered / ContinuedWithRisk

## 问题队列

| 问题ID | 检查点 | 来源阶段 | 标题 | 问题 | 阻塞级别 | mustAsk | 状态 | 关联需求依据 |
|---|---|---|---|---|---|---|---|---|

## 未触发交互的问题

| 问题ID | 未触发原因 | 后续处理 |
|---|---|---|

## 用户回答

| 问题ID | 用户回答 | 回答类型 | 是否进入本次上下文 | 是否建议沉淀 memory |
|---|---|---|---|---|

## 已解决问题

| 问题ID | 原问题 | 解决方式 | 是否从最终待确认问题移除 |
|---|---|---|---|

## 刷新后的未解决待确认问题

| 问题ID | 问题 | 影响 | 保留原因 | 关联需求依据 |
|---|---|---|---|---|

## 本次上下文补充

## 继续分析时保留的待确认风险
```

## 问题设计要求

- 每个检查点一次最多提出 1 到 3 个问题。
- 整次分析建议最多触发 5 个问题；超过部分进入待确认问题。
- 问题必须说明会影响哪些测试分析结论。
- 选项描述要体现取舍，不写空泛描述。
- 至少包含一个“不确认也可继续”的保守选项。
- 用户自定义回答必须逐字保留，不自动泛化为长期事实。
- `Important` 和 `Optional` 默认不触发 `AskUserQuestion`。
- 最终报告的“待确认问题”只保留刷新后的未解决问题，不保留已经被用户回答的问题。
