| 测试数据因子 | 例如：商品状态：上架/下架；库存数量：0-9999；收货地址状态：有效/缺失；用户下单权限：有/无 |

<!--
填写说明：

- 测试点应表达一个明确的规则、风险、路径或条件，写到“要验证什么”的程度，不写成“怎么验证”。
- 测试点可以引用场景测试条件中的业务设计约束、前置条件、角色和测试数据因子，但不展开具体执行路径。

| 兼容性 | 配套兼容性测试 | 验证版本、平台、网络、硬件、配置或软件版本差异下的兼容运行能力。 |

| 可靠性 | 容错容灾测试 | 验证系统在异常、超时、依赖失败、故障注入或恢复场景下的可用和可恢复能力。 |

## 生成规则

- 主输出路径：`${PROJECT_ROOT}/outputs/runs/<run-id>/<需求文件名安全短名>.testcase-design-input.md`。
- 如保留过程分析报告，路径为 `${PROJECT_ROOT}/outputs/runs/<run-id>/<需求文件名安全短名>.test-analysis-report.md`。
- 设计输入文件必须优先满足下游 Test-Design-Agent，不包含方法路由、方法证据、质量门禁、专家评分或 memory 更新建议。
- 设计输入中的测试点 ID 在场景测试点中使用 `TP-001` 连续递增，接口测试点使用 `ITP-001` 连续递增。
- 场景测试点表使用 `测试点 ID | 测试点 | 大类 | 子类 | 级别 | 风险/备注`；接口测试点表使用 `测试点 ID | 测试点 | 大类 | 子类 | 风险/备注`。
- `大类/子类` 使用模板内的类型定义；不要把内部分析方法写入设计输入。
- `待确认信息` 只保留下游设计用例必须知道的问题，已澄清、已覆盖或低风险偏好问题不得保留。
