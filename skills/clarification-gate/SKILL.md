# 交互澄清闸门 Skill

本 skill 用于决定“哪些问题值得优先和用户确认”。它秉持有价值才触发原则：各阶段可以产出澄清候选问题，主会话统一去重、分级和排序后，优先确认会影响测试分析正确性、覆盖范围、风险级别或输出可用性的问题。

## 输入

- 当前检查点名称。
- 当前阶段产物，例如记忆上下文包、结构化需求模型、方法路由表、方法证据、设计输入草稿或覆盖审查结果。
- 已累计的澄清候选问题。
- 已回答的澄清会话记录。
- `${PROJECT_ROOT}/outputs/runs/<run-id>/process/context-pack.md`。
- `templates/clarification-template.md`。

## 检查点

主流程可在以下固定检查点调用本 skill：

| 检查点 | 位置 | 典型候选问题 | 默认策略 |
|---|---|---|---|
| `CP-MEMORY` | `memory-context-builder` 后 | 业务域命中冲突、memory 与需求冲突 | 冲突影响需求理解时优先问 |
| `CP-REQUIREMENT` | `requirement-testability` 后 | 业务规则、状态、权限、边界、接口契约缺失 | 最常触发 Blocking |
| `CP-ROUTING` | `testing-method-router` 后 | 性能、安全、兼容等是否在分析范围内 | 高优先 Important 可问 |
| `CP-METHOD` | 专项方法分析后 | 决策表条件、状态终态、幂等补偿、权限矩阵缺口 | 高风险缺口优先问 |
| `CP-REVIEW` | `coverage-review` 后 | 是否接受带待确认风险的报告、是否补充某类覆盖 | 影响交付可用性时问 |

## 提问触发原则

符合以下任一条件的问题可以进入 `AskUserQuestion` 队列：

1. `Blocking` 问题，无论 `mustAsk` 是否为 `是`，都优先确认。
2. `Important` 且 `priority` 为 `P0` 或 `P1` 的问题，应进入确认队列。
3. 不确认会影响测试点正确性、覆盖范围、风险级别、方法选择或报告是否可交付。
4. 用户尚未回答，也没有被同类问题覆盖。

触发判断采用“先排序、再限流、再提问”的方式。`mustAsk=是` 是强信号，但不是唯一条件；`Blocking`、`Important/P1` 和影响最终测试结论的问题都可以触发。不得因为 `mustAsk=否` 就忽略高影响问题。

以下情况不得打断用户：

- 只是让报告更完整、更好看或措辞更准确。
- 只影响低风险、边缘场景或非核心链路。
- 可由当前需求文档、memory 或知识库中的明确依据解决。
- 与本次需求无直接关系，属于泛化测试好奇心。

## 候选问题来源

各阶段只产出澄清候选，不直接调用 `AskUserQuestion`：

| 来源阶段 | 允许产出候选 | 不允许做什么 |
|---|---|---|
| `memory-context-builder` | memory 冲突、业务域归属不清 | 不要求用户选择所有可能业务域 |
| `requirement-testability` | 影响需求模型的关键缺口 | 不为每个模糊词都提问 |
| `testing-method-router` | 影响方法必要性的范围问题 | 不为了可选方法打断用户 |
| 专项方法 skill | 影响决策表、状态图、权限矩阵、接口契约的关键缺口 | 不追问可作为风险确认点的细枝末节 |
| `testpoint-generation` | 影响测试点粒度或是否保留风险确认点的问题 | 原则上不打断 |
| `coverage-review` | 阻断报告发布的需求缺失 | 不因普通覆盖建议打断 |

## 候选问题字段

每个候选问题应包含：

| 字段 | 说明 |
|---|---|
| 问题ID | 使用 `CQ-001` 递增 |
| checkpoint | 检查点，例如 `CP-REQUIREMENT` |
| sourceStage | 来源阶段或 skill |
| header | 12 个字以内，用于交互问题标题 |
| question | 面向用户的清晰问题 |
| why | 为什么必须确认 |
| impact | 不确认会影响什么 |
| options | 2 到 4 个选项 |
| blockingLevel | `Blocking`、`Important` 或 `Optional` |
| priority | `P0`、`P1`、`P2` 或 `P3` |
| askPolicy | `MustAsk`、`ShouldAsk` 或 `DoNotAsk` |
| mustAsk | `是` 或 `否`，仅表示该问题必须问；不是唯一触发条件 |
| relatedRequirement | 关联需求依据 |
| memoryConflict | 如有冲突，说明冲突的 memory 来源 |

统一候选表头如下，所有阶段必须按此 schema 输出 `CQ-*` 候选：

| 问题ID | checkpoint | sourceStage | header | question | why | impact | options | blockingLevel | priority | askPolicy | mustAsk | relatedRequirement | memoryConflict |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|

字段填写规则：

- `question` 必须能被用户直接回答，避免把多个互斥问题揉在一句话里。
- `why` 说明当前信息缺口，不复述问题本身。
- `impact` 必须落到测试点正确性、覆盖范围、风险级别、方法选择或交付可用性之一。
- `options` 必须互斥，并包含保守继续选项。
- `relatedRequirement` 优先写需求标题、规则句、表格行或段落摘要。
- 同一候选不能同时表达两个独立业务决策；需要拆分时拆成两个候选，再由本 skill 排序限流。

## 优先级规则

| 优先级 | 说明 | 默认交互策略 |
|---|---|---|
| `P0` | 不确认会导致核心业务规则、状态、权限、接口契约或高风险测试点错误 | `MustAsk` |
| `P1` | 不确认会明显影响覆盖范围、风险级别、方法选择或报告可用性 | `ShouldAsk` |
| `P2` | 不确认仍可继续，但会留下普通待确认风险 | `DoNotAsk`，进入待确认问题 |
| `P3` | 只影响措辞、偏好或低风险补充 | `DoNotAsk`，通常不进主输出 |

## 分级规则

以下情况优先标记为 `Blocking`：

- 多条件业务规则缺失，例如优惠叠加、审批优先级、互斥分支或规则优先级。
- 状态迁移不完整，例如终态是否可回退、取消后是否释放资源、失败后是否补偿。
- 权限边界不清，例如角色、租户、归属、数据范围或审批权限不同。
- 金额、数量、时间、次数、配额、阈值等边界缺失。
- 接口失败、超时、重试、幂等、回调或错误码规则缺失。
- 当前需求与 `${PROJECT_ROOT}/outputs/runs/<run-id>/process/context-pack.md` 中已确认事实冲突。
- 需求只出现“合理、快速、稳定、优化”等不可验证表达，且影响核心验收。

以下情况标记为 `Important`：

- 影响覆盖完整性，但可先作为待确认风险点继续。
- 影响可选方法是否展开，例如性能容量、安全风控、兼容性范围。
- 影响风险级别但不改变主业务规则。
- 影响报告是否可直接用于评审或发布。

以下情况标记为 `Optional`：

- 只影响措辞、报告组织或补充说明的问题。
- 不影响核心测试点生成的非关键边界。

## 去重、排序和限流

每次调用本 skill 时必须先处理候选队列：

1. 合并同一业务对象、同一规则或同一状态缺口的问题。
2. 删除已回答或已被当前需求明确覆盖的问题。
3. 按 `priority`、`blockingLevel`、影响范围和需求依据清晰度排序。
4. 当前检查点优先选择 `P0/P1` 问题。
5. 每个检查点建议触发 1 到 3 个 `AskUserQuestion` 问题。
6. 复杂需求的整次分析建议触发 5 到 10 个确认项；普通需求建议触发 3 到 5 个确认项；简单需求可以少问或不问。
7. 如果 `CP-REQUIREMENT` 后仍未触发任何交互，但候选队列存在 `Important/P1`，必须选择影响最大的 1 个问题触发 `AskUserQuestion`，或在澄清会话产物中写明已有明确依据、用户已回答或问题不影响测试结论。

排序时优先级相同的问题按以下顺序比较：

1. 影响核心业务规则、状态迁移、权限边界、接口契约或资损风险的问题优先。
2. 会改变测试方法选择的问题优先于只影响描述完整性的问题。
3. 有明确需求依据的问题优先于泛化风险问题。
4. 能一次回答后解除多个候选的问题优先。
5. 已有保守处理方案的问题可以后置为待确认风险。

## 待确认问题刷新规则

每次用户完成澄清回答后，必须刷新设计输入的待确认信息集合：

1. 已被用户明确回答的问题，从“待确认问题”中移除。
2. 用户选择“暂不确认”的问题，保留为待确认风险点。
3. 用户自定义回答解决了原问题但引入新边界时，移除原问题，并新增更具体的待确认问题。
4. 被当前需求、memory 或用户回答覆盖的同类问题，不重复保留。
5. 未被提问的 `Important` 和 `Optional` 候选只有在仍会影响测试分析结论时，才进入最终“待确认问题”。
6. 设计输入中的“待确认信息”必须是澄清后的未解决问题，不得包含已确认答案的问题。

## AskUserQuestion 使用规则

如果存在 `MustAsk` 或 `ShouldAsk` 的 `P0/P1` 问题，必须优先使用 Claude Code 的 `AskUserQuestion` 交互能力，而不是只输出 Markdown 文本。

- 只在主入口 skill 或主会话编排中触发，由主入口链路统一治理。
- 每轮最多提出 1 到 3 个问题；复杂需求优先一次只问最关键的 1 个。
- 每个问题提供 2 到 4 个明确选项；如果宿主能力只支持更少选项，保留最常见答案和保守继续选项。
- 选项必须包含一个可继续推进的保守选项，例如“暂不确认，作为待确认风险点继续”。
- 宿主 UI 应保留自定义回答入口；用户自定义回答只作用于本次分析，除非后续明确确认写入 memory。
- 用户选择“暂不确认”时，不编造业务规则；把对应内容标记为待确认风险点继续。
- 如果当前运行环境不支持或未暴露 `AskUserQuestion`，不得静默跳过。必须在主会话暂停并输出结构化澄清请求，或在澄清会话产物中记录 `未触发原因=宿主未提供 AskUserQuestion`，设计输入不得把这些问题写成已确认规则。

推荐选项组织：

| 选项类型 | 用途 |
|---|---|
| 明确确认 | 用户选择后可直接修正需求模型或方法选择 |
| 明确保守 | 用户暂不确认时继续分析，但保留待确认风险 |
| 常见替代 | 需求语境下最可能的另一种业务解释 |
| 自定义回答 | 由宿主 UI 提供，不写死在 Markdown 选项中 |

## 会话产物

创建或更新 `${PROJECT_ROOT}/outputs/runs/<run-id>/process/clarification-session.md`，记录：

- 当前检查点。
- 澄清问题队列。
- 未触发原因。
- 用户回答。
- 回答是否进入本次上下文。
- 已解决问题。
- 刷新后的未解决待确认问题。
- 是否建议沉淀到长期 memory。

该文件是运行产物，不是长期 memory。

## 输出

如果无 `MustAsk` 或 `ShouldAsk` 的 `P0/P1` 问题：

- 输出“无需交互澄清”。
- 将未提问但仍有价值的问题按优先级保留为后续报告中的待确认问题或风险确认点。
- 在澄清会话产物中逐项记录未触发原因，原因必须属于“已有明确依据”“用户已回答”“不影响测试结论”“低优先级进入待确认问题”“宿主未提供 AskUserQuestion”之一。
- 刷新未解决待确认问题集合，移除已回答、已覆盖和重复问题。

如果存在 `MustAsk` 或 `ShouldAsk` 的 `P0/P1` 问题：

1. 调用 `AskUserQuestion` 询问用户。
2. 将用户回答写入澄清会话产物。
3. 将已确认答案作为本次运行上下文合并进结构化需求模型。
4. 对选择“暂不确认”的问题，作为待确认风险点继续，不写成已确认规则。
5. 刷新未解决待确认问题集合，确保设计输入只保留尚未解决的问题。

## 失败与降级处理

- 如果候选问题缺少必要字段，先补齐字段；无法补齐时降级为待确认问题，不触发交互。
- 如果多个候选都很重要但超过限流，记录“本轮未问原因=限流后置”，并在后续检查点重新排序。
- 如果用户回答与需求文档冲突，以用户回答作为本次运行上下文，同时在澄清会话产物记录冲突来源。
- 如果用户回答引入新规则，只用于本次报告和 memory 更新建议；不直接修改长期 memory。

## 约束

- 不生成测试点。
- 不生成测试用例或操作步骤。
- 不把用户本次回答自动写入 `memory/project-memory.md`、`memory/domains/*.md` 或 `memory/testing-experience-memory.md`。
- 不为了追求覆盖率而提出无关问题。
- 不把合理推测伪装成用户确认。
- `Optional` 问题默认不触发交互，除非用户明确要求更细澄清。
