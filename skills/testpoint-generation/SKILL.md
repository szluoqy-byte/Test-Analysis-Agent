# 测试点生成 Skill

本 skill 在需求结构化、方法路由和专项分析之后使用，负责把内部分析结果整理成 `templates/testcase-design-input-template.md` 所定义的场景化设计输入。

## 输入

- 结构化需求模型。
- `testing-method-router` 输出的方法路由表。
- `ME-*` 方法分析证据摘要。
- 风险分析结果。
- 边界/等价类、状态、决策表、场景流、权限、接口、数据一致性、组合兼容等分析结果。
- `knowledge/testpoint-standard.md`。
- `knowledge/test-oracle-heuristics.md`。
- `templates/testcase-design-input-template.md`。
- 如需保留过程审查信息，可同时参考 `templates/testpoint-output-template.md` 和 `templates/final-report-template.md`。

## 生成步骤

1. 先按用户任务、业务流程、系统触发、外部交互或专项质量目标识别 `SC-*` 测试场景。
2. 为每个场景填写 `场景名称`、`场景测试类型` 和 `场景目标`；场景名称应是业务行为，不是方法名或测试点分类。
3. 为每个场景补齐 `场景入口/触发方式`、`执行用户/角色`、`前置条件`、`测试数据因子`、`业务设计约束`。
4. 将内部测试点候选归入最合适的场景，并写成“要验证什么”的无歧义验证目标。
5. 场景测试点使用下游类型体系填写 `大类`、`子类` 和 `级别`，不得在设计输入中填写内部 `方法`。
6. 单独识别需要独立验证契约的接口，生成 `接口测试清单` 和 `接口测试详情`；页面观察点或不需独立验证的接口不要强行列入。
7. 接口测试点只描述接口契约、字段、规则、错误码、鉴权、幂等、性能或可靠性目标。
8. 去重并合并过细测试点；如果多个测试点只因具体输入值、按钮或步骤不同而拆分，应上收为规则、条件或风险。
9. 对每个 `必选` 方法检查是否已落到场景测试点、接口测试点、方法证据或待确认问题。
10. 刷新待确认信息，移除已被澄清回答、需求依据、场景条件或测试点覆盖的问题。
11. 填写 `输入完整性自检`，逐项说明是否满足，不保留空说明。

## 标准来源

- 内部分析的 `类型`、`方法`、`级别`、粒度和非用例化约束以 `knowledge/testpoint-standard.md` 为准。
- 设计输入文件中的 `大类/子类` 以 `templates/testcase-design-input-template.md` 的测试点类型定义为准。
- 判定依据启发以 `knowledge/test-oracle-heuristics.md` 为准。

## 合并规则

- 多个专项方法产出的候选指向同一被测对象、同一场景和同一验证特性时，合并为一个测试点。
- 合并后在过程报告中 `方法` 填写最能解释该测试点来源的主要方法；设计输入中不输出 `方法`，其他支撑方法保留在方法证据摘要中。
- 同一业务对象在不同风险维度下需要分别验证时，不强行合并。
- 风险确认点可以生成测试点，但 `风险/备注` 或 `待确认信息` 必须说明依据不足。
- 不把候选表中的临时列带入最终设计输入。

## 输出契约

主输出必须使用 `templates/testcase-design-input-template.md`，并包含以下章节：

- `## 1. 需求信息`
- `## 2. 测试场景清单`
- `## 3. 测试场景详情`
- `## 4. 接口测试清单`
- `## 5. 接口测试详情`
- `## 6. 待确认信息`
- `## 7. 输入完整性自检`

场景测试点表必须使用以下列：

| 测试点 ID | 测试点 | 大类 | 子类 | 级别 | 风险/备注 |
|---|---|---|---|---|---|

接口测试点表必须使用以下列：

| 测试点 ID | 测试点 | 大类 | 子类 | 风险/备注 |
|---|---|---|---|---|

过程报告如包含扁平测试点明细，必须复用同一批场景测试点和接口测试点，不得与设计输入冲突。

## 约束

- 不写操作步骤、具体测试数据或完整预期结果。
- 场景测试条件中可以使用 `前置条件` 和 `测试数据因子`，但不得展开成可执行用例数据。
- 不使用 `操作步骤`、`测试数据`、`预期结果` 作为列名。
- 每条测试点是对验证特性的细化，必须明确被测对象、特定场景和某一功能/规则/行为。
- 每个 `必选` 方法必须产出至少一个测试点或一个待确认问题。
- 每个测试点应能在过程报告中追溯到一个需求依据和一个方法证据；不在设计输入的测试点表中新增证据列。
- 缺少判定依据时，不隐藏问题，标记为“待确认”。
- 本阶段原则上不触发交互澄清；如发现缺口，写入待确认问题或风险确认点。
- 不为了凑数量拆出只有输入值、按钮或页面元素不同的测试点。
- 不使用 `正常`、`异常`、`校验通过` 这类无法单独表达验证特性的描述作为测试点主体。
