# 测试分析方法论

本文档定义 Test-Analysis-Agent 对“测试分析”和“测试设计”的分工理解，以及测试分析阶段应覆盖的分析维度。它是 Analysis 项目的上位方法论，用于指导 `requirement-testability`、`testing-method-router`、专项分析 skill、`testpoint-generation` 和质量门禁。

## 核心边界

| 阶段 | 回答的问题 | 主要产物 | 不做什么 |
|---|---|---|---|
| 测试分析 | 测什么、为什么测、覆盖哪些条件和风险 | 测试场景、场景测试条件、测试点、接口测试点、待确认问题 | 不写完整测试步骤、具体执行数据和完整预期结果 |
| 测试设计 | 怎么测、用哪些数据/步骤/预期来测 | 测试用例、测试数据、前置步骤、测试步骤、预期结果 | 不重新补 Analysis 遗漏的业务规则和上下文 |

Analysis 与后续 Design 是独立项目。Analysis 的主交付件是唯一跨项目输入，必须自包含到后续设计项目只读取该文件也能开展用例设计。

## 测试分析维度

| 分析维度 | 关注对象 | 典型方法/Skill | 主交付件落点 |
|---|---|---|---|
| 需求可测性 | 需求目标、验收标准、可观察结果、歧义和缺口 | `requirement-testability` | 需求信息、待确认信息、场景目标 |
| 风险与优先级 | 失败模式、影响范围、资损/越权/不可逆/历史缺陷 | `risk-based-test-analysis` | 级别、风险/备注、待确认信息 |
| 业务场景与流程 | 用户旅程、系统触发、主流程、备选流程、异常流程 | `scenario-flow-analysis` | `SC-*` 场景、场景入口/触发方式、场景目标 |
| 数据域与边界 | 金额、数量、时间、状态、枚举、格式、容量 | `boundary-equivalence-analysis` | 测试数据因子、业务设计约束、规则级测试点 |
| 业务规则组合 | 多条件、多角色、多状态、开关共同决定结果 | `decision-table-analysis` | 业务设计约束、规则组合测试点、待确认信息 |
| 状态与生命周期 | 初始状态、中间状态、终态、非法迁移、重试、超时、补偿 | `state-transition-analysis` | 测试数据因子、业务设计约束、状态规则测试点 |
| 权限与数据范围 | 角色、资源、动作、数据归属、租户、审批权限 | `permission-role-analysis` | 执行用户/角色、权限边界测试点、待确认信息 |
| 接口与契约 | API、字段、错误码、鉴权、幂等、回调、超时、版本兼容 | `interface-contract-analysis` | 接口测试清单、接口测试详情、接口补充说明 |
| 数据一致性 | 主数据、派生数据、缓存、统计、搜索、导出、日志、外部系统 | `data-consistency-analysis` | 数据因子、业务设计约束、数据一致性测试点 |
| 组合与兼容 | 平台、版本、配置、渠道、语言地区、feature flag | `combinatorial-compatibility-analysis` | 测试数据因子、兼容性场景、关键组合测试点 |
| 非功能质量属性 | 性能、可靠性、安全、易用性、服务化、部署 | `risk-based-test-analysis`、`testpoint-generation` | 场景测试类型、专项场景、指标/约束/待确认信息 |
| 经验与缺陷模式 | 历史缺陷、错误猜测、检查清单、缺陷分类 | `risk-based-test-analysis`、`knowledge/defect-patterns.md` | 风险/备注、补充测试点、待确认信息 |

## 方法与维度的关系

- 分析维度回答“这段需求从哪个角度需要被看见”。
- 测试方法回答“用什么分析手段识别测试条件和覆盖项”。
- 测试点回答“交付给后续设计项目时，要验证什么”。
- 测试用例回答“具体怎么执行和判定”，不属于 Analysis 主交付件。

边界值、等价类、决策表、状态迁移等在业界常被称为测试设计技术；在 Analysis 项目中，它们只作为识别测试条件和覆盖项的分析手段。方法产物可以保留在过程报告中，但主设计输入只呈现业务规则、数据因子、场景条件和验证目标。

## 主交付件落点规则

| 分析发现 | 主交付件写到哪里 | 不应写成 |
|---|---|---|
| 业务目标和范围 | `需求信息`、`本次不覆盖内容` | 见原始需求 |
| 用户旅程、系统触发、跨系统流程 | `测试场景清单`、`场景入口/触发方式` | 点击路径步骤 |
| 角色、资源、权限边界 | `执行用户/角色`、权限测试点 | 账号级测试数据 |
| 状态集合、枚举、金额/数量/时间范围 | `测试数据因子` | 具体用例数据表 |
| 业务规则、异常处理、约束 | `业务设计约束`、测试点 | 判定表行、边界值清单 |
| 接口、字段、错误码、幂等、回调 | `接口测试清单`、`接口测试详情`、接口补充说明 | 具体请求报文步骤 |
| 未确认但影响设计的问题 | `待确认信息` | 当作已确认规则 |
| 高风险或历史缺陷启发 | `风险/备注`、待确认信息 | 编造需求没有的规则 |

## 质量要求

- 每个重要需求片段至少要落到一个测试场景、接口对象、测试点或待确认问题。
- 每个必选分析维度要有方法证据、测试点承接或待确认问题解释。
- 主交付件必须自包含，不能要求后续设计项目回读原始需求、过程报告、memory、context-pack 或 Analysis knowledge。
- 主交付件不能泄漏方法产物，例如边界值清单、等价类清单、判定表、组合矩阵或状态迁移矩阵。
- 待确认信息只保留会影响后续用例设计的问题，已回答或低价值偏好问题不得保留。
