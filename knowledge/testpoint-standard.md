# 测试点标准

## 定义

测试点是对验证特性的细化，用直观、明确、无歧义的语言，描述被测对象在特定场景下的某一功能、规则或行为。测试点不是测试用例。

## 测试点必须包含

- ID。
- 模块。
- 验证目标。
- 类型。
- 使用的方法。
- 需求依据。
- 级别。
- 风险或备注。

## 测试点不得包含

- 前置条件。
- 分步骤操作。
- 具体测试数据清单。
- 完整预期结果。
- 自动化代码。

## 标准类型

- 功能正确性
- 业务规则
- 异常容错
- 边界值
- 状态迁移
- 权限角色
- 数据一致性
- 接口契约
- 兼容性
- 性能容量
- 安全风控
- 可观测性

## 标准方法

- 风险驱动
- 需求可测性
- 边界值
- 等价类
- 状态迁移
- 决策表
- 场景流
- 权限矩阵
- 接口契约
- 数据一致性
- 组合兼容
- 错误推测
- 可观测性审计

## 粒度示例

- 过粗：`验证登录功能正常`。
- 合适：`验证登录表单在密码错误场景下的登录失败处理和失败提示符合需求`。
- 过细：`输入 abc 点击登录检查提示`。
- 方法可见：`方法=决策表`，`测试点=验证不同会员等级与优惠券状态组合下的优惠适用规则`。

## 反例库

| 问题 | 反例 | 修正方向 |
|---|---|---|
| 过粗 | `验证订单功能正常` | 明确被测对象、场景和验证特性 |
| 过细 | `输入 100 元点击提交检查结果` | 合并为金额边界或等价类测试点 |
| 用例化 | `先登录，再进入订单页，点击取消按钮` | 去掉步骤，描述验证目标 |
| 无依据 | `验证管理员可以强制取消所有订单` | 如果需求未说明，改为待确认问题 |
| 方法不匹配 | `类型=权限角色，方法=边界值` | 按实际分析方法填写权限矩阵 |
| 风险备注空泛 | `风险较高` | 说明资损、越权、不可逆、数据一致性等原因 |

## 表达结构

测试点文本优先使用以下结构：

```text
验证 <被测对象> 在 <特定场景> 下的 <某一功能/规则/行为> 是否符合需求
```

描述约束：

- 被测对象：具体到功能组件、业务对象、接口、状态对象或数据对象，避免只写系统名。
- 场景：说明触发条件、用户角色、状态、输入域、流程分支、异常条件或兼容环境。
- 验证特性：说明要验证的功能、业务规则、状态迁移、契约、权限或数据一致性。
- `测试点`：用自然语言把被测对象、场景和验证特性组合成无歧义验证目标。

## ID 与级别

- ID 格式：`TP-001`、`TP-002`，按顺序递增。
- 级别取值：`Level 0`、`Level 1`、`Level 2`、`Level 3`、`Level 4`。

## 级别定义

本系统不生成测试用例；以下定义沿用测试用例执行分级语义，映射为测试点后续转用例、版本验证和回归选择时继承的重要度。

- `Level 0`：核心。最核心的功能用例，建议每个转测试的版本都验证；执行失败意味着版本核心功能受损，没有继续验证的价值。
- `Level 1`：关键。涉及系统特性的关键功能、关键可靠性等内容的用例，建议每个迭代验证；执行失败即特性内某个关键功能点测试出现阻塞问题。
- `Level 2`：重要。覆盖系统所有重要功能的用例，建议 TR 点或对外发布版本进行完整验证，以保障系统功能正常实现。
- `Level 3`：一般。版本全量测试较为完整的测试用例，建议版本变更较大、需要全量验证覆盖时，根据版本修改点涉及范围，选择变更较大的特性相关部分或全部用例作为回归范围。
- `Level 4`：生僻。对于较生僻的应用场景和预置条件，是版本不常用场景的用例，建议新特性首次验证使用；验证通过后，大多数情况不需要回归执行。
