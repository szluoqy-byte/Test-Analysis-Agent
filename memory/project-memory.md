# 项目 Memory

本文件是项目 Memory 的全局高优先级规则。它回答“这个项目已经确认过什么”，并为按需扫描的业务域分片提供全局上下文。

业务域、业务术语、角色权限、接口约定、数据约定和设计约束较多时，不在本文件堆叠全文；按业务域拆到 `memory/domains/*.md`。`domains/` 是用户自定义扩展区，新增 `.md` 分片后由 `memory-context-builder` 自动扫描和匹配，不需要在本文件建立索引。

## 加载约定

1. 每次分析开始前，先读取本文件中的全局项目事实、全局约束和输出偏好。
2. 自动扫描 `memory/domains/*.md` 分片，跳过 `README.md`，根据文件名、标题、适用范围、关键词、领域术语、角色、接口、状态和数据对象选择相关分片。
3. 只把与本次需求直接相关的全局内容和业务域分片摘要注入 `${PROJECT_ROOT}/outputs/runs/<run-id>/context-pack.md`。
4. 如果 memory 与当前需求文档冲突，不直接覆盖需求，以“待确认问题”输出。
5. 未经用户或评审明确确认的业务规则，不写入长期 memory。

## 全局项目事实

- 项目名称：Test Analysis Agent。
- 当前目标：基于 Markdown 需求文档生成测试点分析报告。
- 当前范围：v1 每次处理一份 Markdown 需求文档。
- 主要产物：完整测试点分析报告和独立测试点明细文件。

## 全局高优先级规则

- 当前需求文档中的明确规则优先于历史 memory。
- memory 只能提供项目语境、已确认事实和风险启发，不能替代需求依据。
- 缺少业务规则、边界、状态、权限、接口返回或异常处理依据时，输出待确认问题。
- 测试点必须保持可追踪，不能脱离需求依据或风险确认点。
- 方法路由、方法证据、测试点生成和覆盖审查必须形成可追踪链路。
- Memory 只保存经确认的项目事实和项目经验，不保存未确认假设。

## 全局领域术语

| 术语 | 含义 | 来源 | 备注 |
|---|---|---|---|
| 需求文档 | 输入给 Agent 的 Markdown 产品或业务需求说明 | 项目设计 | v1 只支持单文件 |
| 测试点 | 采用 `knowledge/testpoint-standard.md` 中的定义 | 用户确认 | 不拆成被测对象、场景、验证特性三列，统一写在测试点描述中 |
| 需求依据 | 测试点对应的需求标题、段落、表格行或规则摘要 | 项目设计 | 用于可追踪性 |
| 方法证据 | 专项测试方法分析后的 `ME-*` 证据摘要 | 项目设计 | 用于证明测试理论被实际应用 |
| 记忆上下文包 | 每次分析前从长期 memory 中筛选出的本次上下文摘要 | 项目设计 | 写入 `${PROJECT_ROOT}/outputs/runs/<run-id>/context-pack.md`，作为运行产物保存 |
| 业务域分片 | 某个业务或项目子域的长期 memory 文件 | 用户确认 | 位于 `memory/domains/*.md`，由加载流程自动扫描 |

## 全局输出偏好

- 输出使用 Markdown。
- 测试点按模块组织，粒度保持中等。
- 测试点表包含 `方法` 列，体现使用的测试理论方法。
- 测试点表包含 `级别` 列，取值为 `Level 0` 到 `Level 4`。
- 最终报告包含测试方法路由、质量门禁结果、专家评分和建议沉淀的 Memory 更新。
- 测试点明细需要额外单独保存一个文件。
- 独立测试点明细只保留测试点明细表和必要元信息，不包含覆盖审查、质量门禁、专家评分或 memory 更新建议。

## 全局非范围

- 不生成测试用例。
- 不生成测试执行步骤。
- 不生成自动化脚本。
- v1 不引入数据库、向量检索或服务端存储。
